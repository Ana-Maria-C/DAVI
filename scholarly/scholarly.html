1. Abstract

DAVI (Data Visualization & Interaction) is a modular Single Page Application (SPA) designed to transform static movie datasets into an interactive Knowledge Graph. By leveraging the Semantic Web stack (RDF, SPARQL, Ontologies), DAVI moves beyond traditional relational database limitations, allowing users to explore movies through their hidden connections, shared genres, common tags, and implicit relationships.

The system implements a microservices architecture using FastAPI as an API Gateway and Apache Jena Fuseki as the triple store. The frontend, built with Angular 21, features advanced visualizations including a 3D Force-Directed Graph and interactive charts, providing users with a "big picture" view of the MovieLens 100k dataset.

2. Project Motivation

In the modern digital landscape, recommender systems are often "black boxes." Users are fed suggestions without understanding why. DAVI aims to democratize this data by:

  • Visual Transparency: Users can literally "see" the connections between a movie they like and its neighbors in the graph.
  • Semantic Reasoning: Instead of simple text matching, the system understands that "Family-friendly" is a sub-category of "Comedy," enabling smarter filtering.
  • Educational Value: Demonstrating how Linked Data principles can be applied to real-world entertainment datasets.

3.2 Technology Stack

We selected a modern, robust stack to ensure high performance and developer ergonomics:

Frontend (Client)

  • Framework: Angular 21 (Latest) - for component-based logic.
  • Visualization:
    • 3d-force-graph: WebGL-powered graph rendering.
    • ngx-charts: For statistical bar/pie charts.
  • UI Library: Angular Material - ensuring a consistent, accessible design.
  • State Management: RxJS - handling asynchronous data streams (filters, search results).

Backend (Server)

  • Framework: FastAPI (Python 3.9+) - High-performance, async I/O.
  • Validation: Pydantic - Data validation and settings management.
  • RDF Tools:
    • SPARQLWrapper: For executing queries against Fuseki.
    • rdflib: For parsing and serializing Turtle (`.ttl`) files.

Data Persistence

  • Triple Store: Apache Jena Fuseki.
  • Format: RDF/Turtle.
  • Containerization: Docker & Docker Compose.

3.3 System Architecture and API Structure

The backend exposes a RESTful API that abstracts the complexity of SPARQL. It transforms frontend JSON requests into SPARQL queries, executes them, and formats the results back to JSON.

Level 3: Components

The Component diagram breaks down the API Application into its core modules: Controllers, Services (Business Logic), and Repositories (Data Access).

Key API Controllers:

  • Movies Controller (`/api/movies`):
    • GET /: Retrieve all movies.
    • POST /: Create a new movie.
    • GET /search: Core search engine with filters (genre, year, rating).
    • GET /search_by_title: Text-based search for movie titles.
    • GET /compare: Compare multiple movies side-by-side.
    • GET /graph: Data optimized for the 3D visualizer (Nodes/Links).
    • GET /{movie_id}: Retrieve detailed movie metadata.
    • PUT /{movie_id}: Update movie information.
    • DELETE /{movie_id}: Delete a movie (cascading).
  • Analysis Controller (`/api/analysis`):
    • GET /stats: System-wide statistics (counts, distributions).
    • GET /facets: Filter facet data.
    • GET /trends/famous: Most popular (reviewed) movies.
    • GET /trends/rated: Highest-rated movies.
    • GET /trends/yearly/{year}: Trends for specific years.
  • Auxiliary Services:
    • GET /api/genres: Genre hierarchy for smart filtering.
    • POST /api/ratings: Submit user ratings.
    • GET/POST /api/sparql: Direct SPARQL query execution.

4. Knowledge Model & Semantics

Unlike a SQL schema, our data model is a flexible graph defined by an Ontology. We manually designed the schema using schema.ttl to persist it, ensuring full control over the semantic structure.

4.1 RDF Class Structure

The ontology defines the following core classes and properties, mapped meticulously to Schema.org:

  • :Movie (owl:Class)
    • Subclass of: schema:Movie.
    • Derived from: :MovieLensDataset (Provenance).
    • Properties: :hasGenre (ObjectProperty -> :Genre), :hasTagLabel (DatatypeProperty -> xsd:string).
  • :User (owl:Class)
    • Subclass of: schema:Person.
    • Role: Connects to movies via reified ratings.
  • :Genre (owl:Class)
    • Subclass of: schema:DefinedTerm.
    • Logic: Uses :subCategoryOf (Transitive Property) to create a hierarchy (e.g., :War -> :Emotional).
  • :Rating (owl:Class)
    • Subclass of: schema:Rating.
    • Context: Resolves the N-ary relationship between User, Movie, and Value.
    • Properties: :ratedBy (User), :ratingOf (Movie), :ratingValue (float).

The schema also includes custom inference rules. For example, we introduced high-level super-categories (genre:Emotional, genre:Exciting, etc.) to allow the system to infer that an Action movie is also Exciting.

4.2 Linked Data Principles

DAVI respects the 5-star Linked Data principles:

  1. OL: Data is available on the web (Open License).
  2. RE: Data is machine-readable (RDF/Turtle).
  3. OF: Non-proprietary format (CSV -> converted to TTL).
  4. URI: All entities have URIs (e.g., http://example.org/movielens/Movie/1).
  5. LD: (Planned) Links to extensive context via DBpedia.

5. External Data & SPARQL

The system transforms the raw MovieLens 100k dataset (CSV) into a semantic graph. The transformation logic convert_csv_to_rdf.py cleans the data, handles missing values, and mints URIs.

5.1 Advanced SPARQL Queries

The application provides a dedicated interface for executing raw SPARQL queries directly against the Knowledge Graph. This allows power users to explore the data without UI constraints.

We implement non-trivial queries to extract insights. For example, to find movies that bridge multiple high-level emotional spectrums (e.g., both "Intellectual" and "Exciting"), we use an aggregation query that groups inferred super-categories: 


PREFIX : <http://example.org/movielens/>
PREFIX schema: <http://schema.org/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?title (GROUP_CONCAT(DISTINCT ?moodLabel; separator=" + ") AS ?complexMood) (AVG(?rVal) AS ?avgRating)
WHERE {
    ?m a :Movie ;
       schema:name ?title ;
       :hasGenre ?g .
    
    ?g :subCategoryOf* ?superG .
    ?superG rdfs:label ?moodLabel .
    
    # Filter for top-level mood categories
    FILTER(?superG IN (
        <http://example.org/movielens/Genre/Emotional>,
        <http://example.org/movielens/Genre/Exciting>,
        <http://example.org/movielens/Genre/Intellectual>,
        <http://example.org/movielens/Genre/FamilyFriendly>
    ))
    
    # Collect ratings
    OPTIONAL { 
        ?r :ratingOf ?m ;
           :ratingValue ?rVal .
    }
}
GROUP BY ?title
HAVING (COUNT(DISTINCT ?superG) >= 2)
ORDER BY DESC(?avgRating)
LIMIT 5

6.1 Use Case: Exploring Relationships via 3D Graph

Scenario: A user wants to find "clusters" of related movies visually rather than scrolling a list.

Visualization Details:

  • Grey Nodes = Movie Entities (Central hubs).
  • Purple Nodes = Genres.
  • Blue Nodes = Movie Titles.
  • Turquoise Nodes = User Tags.
  • Orange Nodes = Ratings.

Graph Search:

When investigating specific nodes, the graph highlights direct connections:

  • Yellow Nodes = Search matches (e.g., "Star Wars").
  • Red Nodes = Directly adjacent nodes (connected genres, tags, etc.).

7. Future Development Roadmap

While the current iteration meets the core WADe requirements, we envision several enhancements for Version 2.0:

Phase 1: Enhanced Intelligence

  • Collaborative Filtering: Implement Matrix Factorization (ALS) to suggest movies based on user similarity, not just metadata.
  • Federated Queries: Execute live SPARQL queries against DBpedia to fetch the latest director info and actor biographies.

Phase 2: Social Features

  • User Accounts: Fully implement JWT authentication.
  • Watchlists: Allow users to save custom lists to the Knowledge Graph.
